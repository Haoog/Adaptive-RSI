## Install on your phone

Choose **Install on phone** in the console sidebar and open the actual installation link. Alternatively, append `/install` to your HTTPS console origin. The installation page contains no login credential and can be saved. Use login links containing `?token=` only on your own devices.

- Android: open the page in Chrome, tap Install, or use Install app in the browser menu.
- iPhone / iPad: open it in Safari, then Share → Add to Home Screen. Opening from the home screen may require logging in again.
- This is a browser-installed PWA without an APK or App Store package. Execution remains on the computer or server; the phone provides monitoring and controls.

Your phone cannot reach your computer's `127.0.0.1`. Configure a reachable HTTPS origin using [Server deployment](SERVER.en.md), sign in on your phone with the runtime-generated login link, then open installation. Neither the manifest nor shortcut stores a token. The service worker does not cache API responses, code or private pages. A network connection is required.

Minimum requirements follow the browser: the console needs a modern browser equivalent to iOS 15.4+ or Android 8+ (requires `structuredClone` and PWA support). Older systems render a blank page; upgrade the system or use the desktop app instead.

## Tasks and recovery

The submit button retains the original text, content digest and request ID for up to 32 unconfirmed goals per project in the current browser session. After changing text or reloading, select an unconfirmed goal in the form to restore its text, then submit explicitly using its original ID. Restoring replaces the current draft without sending automatically. Success removes only the matching record, freeing capacity for new goals. Legacy digest-only records require the original text to match. Invalid records or storage failures prevent sending without a retained deduplication ID. Retrying an ambiguous response returns the original task; submitting after success creates a new task. CLI users can specify `goal --request-id`. Reusing an ID with different content is rejected; project submissions remain isolated.

Shared and project settings remain editable while saving. Later drafts survive project switches, including edits back to values from before the save, and can be explicitly saved or undone on return. Success confirms only the submitted values and compares unsaved edits against the newly saved values.

Saving inspection or Issue-sync intervals reschedules the next check; an older finishing scheduler cycle cannot overwrite that plan. Project overrides remain separate from shared settings. Next times follow working hours in the runtime machine's local timezone. When daylight saving skips an entire window, the next check moves to an actually existing eligible time.

Newly claimed tasks use the settings saved before their claim; active runs retain their sealed settings. Pausing retains a stop request for current runs, and quickly resuming does not withdraw it. Interrupted tasks can be explicitly retried. Editing or removing a model connection retains its old credential until referencing runs finish, after which periodic maintenance removes it.

The queue shows ordering, urgency, and reasons for waiting: pause, backoff, working hours, current work or a predecessor. Urgency is separate from value. A waiting task can depend on another task in the same project. Once that task merges, downstream work starts from a fresh baseline. Cycles are rejected, and independent work can proceed. Dependency candidates load at most 200 tasks per page; use Previous and Next to reach older tasks. Paging keeps the selected dependency without automatically downloading all history. Unsaved dependency and priority edits survive language changes, requirement supplements and task-state refreshes; click “Save queue settings” to apply them. Closing details or switching tasks or projects ends the current queue draft. While a task save is pending, rebuilt details cannot submit another queue save. Edits made after submission, including undoing to earlier values, remain as later drafts; the acknowledgement confirms only the submitted values. A queued task waiting on backoff offers “Retry now” in the list and detail to run early and clears its infrastructure retry count; ordinary queued tasks do not show this entry.

After cancellation, retrying or supplementing requirements waits until the active run has stopped completely. The dashboard explains this wait. Manual retries and requirement supplements invalidate undelivered candidates and their queued approvals, requiring fresh verification. Existing PRs and merge records remain available. Failed remote closes of stale PRs retain reconciliation intent; old tracking cannot terminate replanned work. Local Issue supplements are stored separately from upstream text and combined into new task input during synchronization. Historical supplements cannot be recovered automatically if both the overwritten text and its revision history have already been removed. An empty supplement, one over 10,000 characters, or a combined Issue requirement over 30,000 characters is explained inside the form instead of surfacing only a generic error.

Deferral decisions persist independently of runs, including reason, input fingerprint, baseline and wake conditions. Identical inputs do not requeue repeatedly. Only an explicitly complete dependency-path record can suppress unrelated changes. Implementation scope or an issue location alone is insufficient; uncertain relationships trigger conservative reassessment. Supplement requirements on the same task to retain revisions and invalidate stages based on older inputs. Deferred and rejected decisions from batch triage are written to the same decision store when the finding lands; the reason shows in the task list and detail, and rejected work is reconsidered manually via retry or requirement supplements.

Ordinary code tasks schedule up to three retries with jittered backoff for timeouts, rate limits and transient network failures, separately from code repair attempts. Every retry creates a fresh isolated run. Background inspections and strategy experiments retain their existing schedules and manual retry path; they are outside this automatic backoff and connection-resume scope. Authentication, protocol, checks and review failures do not receive transient recovery. Resuming a connection in Model Center only resumes matching temporary failures for that project and connection revision. Cancellation, pause, old connections and uncertain remote deliveries cannot be bypassed.

Retry feedback retains specific review locations, consequences and suggestions, plus bounded failed regression summaries. Protected independent acceptance sources remain excluded. When protected samples exist, a feedback field rewritten by URL or credential redaction is hidden in full to avoid exposing sample remnants; other fields still provide bounded specific feedback. Rejected candidates still require implementation, checks and review again. Plans can declare behavior, performance, refactor, documentation, configuration or UI changes. Defect fixes still need behavioral evidence and cannot evade gates through reclassification.

Performance tasks freeze a metric, unit, target, tolerance and direction before implementation. Independent checks report measurements for each version. The host verifies the target and an improvement exceeding tolerance; missing thresholds or matching measurements yield insufficient evidence. Preservation contracts require an explicitly behavior-preserving request. Other types demonstrate the requested before/after change and still require fixed regressions and independent review.

With automatic promotion off, verified candidates remain in a ready state and can be enabled manually after confirmation. Only ready candidates are accepted; enabling replaces the stable strategy of the same project and kind, starts limited monitoring, preserves the paired evidence and rolls back step by step through the immediately preceding verified strategy. The page shows used/limit exposure per split and separates independent-case counts from total paired runs. Exhausted exposure explains how to import new cases or raise `evolution.max_holdout_uses` instead of only reporting insufficient samples. Rollbacks, imports and promotions refresh candidates and statistics immediately; other polling keeps its cache interval.

## Results and attention

Task details load the latest run first and fetch historical runs on expansion. Current state updates periodically; task URLs support direct navigation. Saved checkpoints are distinguished from actual execution. No fabricated percentages or completion estimates are shown. Results include independent before/after acceptance, review findings and readable diffs; original evidence is preserved. Unbroken long text and long URLs in sources, evidence and revisions wrap inside the detail instead of scrolling horizontally.

The **Attention inbox** covers every project. System notifications require opt-in and fire on new states or reasons. Unchanged polling stays quiet. Denied notification permission does not remove inbox items, and viewing a notification does not resolve work. Browser notifications navigate to tasks. When the desktop notification service reports a click, the window opens the corresponding task. Notifications from a previously connected runtime cannot navigate into another runtime. Web Push while the page or desktop client is closed is not provided.

Usage list searches update after typing stops. Earlier responses cannot cancel new searches or replace later results; switching projects or leaving the page invalidates old requests.

**Records and usage → Workflow quality and timing** reports logical tasks created in the last 30 days: first pass, acceptance, merges, infrastructure failures, repeated failures, revisions and reused stages. Accumulated phase durations include parallel runs and are not total elapsed time. Unknown usage remains explicit rather than becoming zero. These metrics do not establish model capability improvements.

Metrics also report average time to PR and merge with sample counts, repeated failure signatures, user interventions, tokens per accepted/delivered task, invalidation reasons and recorded CI/review waits. Missing historical wait durations are not fabricated. Preparation, model calls, checks and review are recorded separately.

## Backups and retention

**Data and diagnostics** provides storage totals, consistent online SQLite backups, downloads and diagnostic previews. Backups contain private task content and configuration; keep them private. Diagnostic summaries include only version, counts, failure codes and storage size, excluding credentials, paths, code, task text and full prompts.

Backups remain absent from the download list while being generated. They become downloadable only after copying, portability preparation and file closure, preventing incomplete snapshots from being exported as successful backups. Failures remove staging files without overwriting existing backups. The pending-approval count in **Data and diagnostics** includes only candidates that can still be approved; approved, delivering and cancelled candidates are excluded, and in-progress deliveries are reported separately.

A failed restore removes only the state directory it newly created while empty, keeps the original error, and can be retried immediately. Existing directories, user data and symlink targets are never deleted.

Restore into a new state directory:

```sh
adaptive-rsi --state-dir /NEW/STATE restore /PATH/BACKUP.sqlite3
```

Existing state is never overwritten. Restored projects remain paused, active runs become interrupted, old candidate approvals expire, and queued deliveries are blocked for reconciliation. Imported runs stop using source-state artifact paths and local verification caches expire; known PR receipts and remote delivery records remain. Missing acceptance or dependency artifacts produce insufficient evidence during post-merge verification. Supply trusted artifacts inside the current state directory or verify again; evidence from another directory cannot be reused. Database backups exclude candidate workspaces and machine credentials. On another machine, reconnect credentials, verify project paths and remote delivery state before enabling projects.

Candidate files expire under project retention settings and cannot be approved afterward. Retry expired tasks to verify the latest code again. Original summaries remain; cleanup does not imply successful delivery. When restoring from a database backup, undelivered candidates are invalidated because candidate files are not in the backup; the interface states this restore reason instead of reporting retention cleanup.

## Cancellation Previews, Revisions and Intervention History

Selecting **Cancel task** in task details first displays downstream impact. Only the current task is cancelled by default; **Also cancel eligible downstream tasks** explicitly expands the scope. Finished or delivered tasks retain their state. If tasks or dependencies change before confirmation, the entire operation is rejected and requires another preview. Large dependency chains preview at most 999 downstream tasks and disclose truncation. The current task can still be stopped, but an incompletely previewed cascade is forbidden. Cancellations and per-item audit events commit together.

**Requirement revisions** loads each diff and complete before/after text when expanded, with more history available through pagination. New revisions atomically retain the resulting snapshot, input hashes and candidate invalidation effects; later runs require fresh verification. Older entries without resulting snapshots retain their original supplements and state the missing evidence explicitly. They do not infer the final requirements. Above 2,000 lines, complete before/after text replaces expensive diff computation. History remains subject to retention policies.

Cancellation, revision and approval can include an optional reason, retained verbatim without translation or rewriting. **Human intervention history** provides timestamps, original reasons and raw effects for retries, cancellations, queue changes, revisions and approvals. Approval records identify the candidate and publication task. Older records may lack reasons or complete before/after states; that does not imply no human intervention occurred.

**Export loaded intervention records** exports only records already loaded. The JSON `complete` and `next_before` fields disclose remaining pages; load more before exporting when needed. Pagination follows stable record IDs backward so newly arriving operations do not displace older pages being inspected.

Task groups: failed or cancelled groups can be split for fresh verification. The confirmation lists restored originals and discloses any separate task retaining the complete revised specification. Revised unstarted groups cannot be directly ungrouped, preventing lost supplements. Group lineage and outcomes retain failed runs and source relationships, with pagination for older history.

During desktop replacement, admission stays closed while the installer process is alive, regardless of elapsed time. If the owned installer exits before stopping the service, admission recovers with an audit record and tasks remain intact. Unknown process status keeps the barrier closed; legacy barriers recover through the owned desktop restart or explicit lease cancellation.

Queue settings support up to 100 predecessor tasks and a combined ancestry budget of 1000 nodes. All predecessors must merge before a task can start. Cycles, missing nodes and cross-project dependencies are rejected. A failed or cancelled predecessor blocks its dependent for manual review while retaining unrelated prerequisites. Multi-selection survives paging, language changes and live detail refreshes.

Experiment cards compare paired quality, token usage (not currency) and latency, with real/synthetic and task-size cohorts. Unknown usage and zero baselines remain incomparable; observed subgroup losses remain visible. Expand a card to inspect or export its recorded plan, input manifest and evidence. Native tool activity records invocation hashes, status and timing without arguments, source text or command output. Interrupted search retains bounded file/line locations. A started step without a terminal receipt needs investigation and is never automatically replayed. Source reads check cancellation between 64 KiB chunks and search checks every 256 lines; an individual blocked operating-system filesystem call cannot be interrupted by these cooperative checks.

Database diagnostics correlate slow query fingerprints with opaque request/task/run IDs, separating SQL execution from connection waiting and excluding SQL text and bound parameters. Pool wait quantiles include capacity timeouts and declare their process/window scope. Normal metrics do not perform full relationship scans; explicit diagnostics inspect ownership and evidence links, disclosing per-check truncation. Explicit orphan-stage quarantine is transactional and bounded, retains every original column, and does not automatically delete other kinds of evidence.

Open Settings change history to page through revision sources and redacted differences. Undo restores the exact previous sparse overrides and creates a new audited revision; active runs retain their snapshots. Revision, project ownership and content hashes are checked before undo, so later edits in another window or global settings reject stale requests. Unsaved local drafts remain available. Exact undo snapshots stay in private SQLite storage; ordinary activity endpoints omit credential values. Legacy raw audit evidence remains in the private database. Snapshot rotation is not yet automatic; treat database backups as sensitive data.

Mobile diff reading: open Read code diff, expand individual files, or use Collapse all files / Expand all files. Narrow screens wrap by default and wrapping remains manually selectable. Search and hunk navigation open the target file; unopened files defer content-node creation. Diffs exceeding 2000 lines use plain text per file; search scrolls using the actual layout rather than assuming fixed-height unwrapped lines. Server artifact size bounds still apply. Expanding all files may increase browser memory use.

Blocking-cause chains: queued or attention-needed tasks can expand Why has this not started? to inspect unmerged prerequisites and their causes, alongside project pause, retry time, active work, global concurrency capacity, working hours, resource pressure, updates and imports. Refresh rechecks conditions; clearing one cause does not hide the others. Only current-project titles are returned. Corrupt historical dependencies pointing to another project show only an identifier and invalid-dependency cause. Traversal/display is bounded to 1000 nodes/edges, and truncation explicitly does not prove omitted causes are absent. This view explains observations without retrying tasks, releasing update leases or performing recovery; admission leases awaiting reconciliation remain visible.

Structured errors: settings validation returns a general error type, stable reason code and allowlisted field path. The UI provides equivalent Chinese/English guidance without reflecting arbitrary input fields or values from exception text. Unknown HTTP errors retain the server X-RSI-Request-ID through Copy diagnostic ID; if clipboard access is denied, a manually copyable ID is shown. Expanded raw diagnostics retain status, reason, field and request identity. Nonconfiguration service failures continue to use existing error codes or safe generic guidance; arbitrary runtime strings are not all statically translatable.

Browser navigation: Back and Forward replay routes without adding history entries. An initial page without a hash records its original project, allowing a first-action project switch and later reload/back navigation to restore that project. The project selector and data stay synchronized. Notification task routes retain project and page parameters; closing details removes only the task parameter. Programmatic close, close button, Escape and backdrop clicks consistently identify old close events so they cannot cancel a new notification while refresh is pending. Goal/settings drafts stay scoped to their projects; navigation itself does not submit tasks.
